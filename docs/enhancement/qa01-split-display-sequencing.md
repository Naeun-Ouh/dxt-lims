# QA-01 — Split Group display sequencing

2026-11-27. Implements the replacement Product Owner policy; supersedes collision-avoidance naming. This is display sequencing, not Group revision management.

## Behavior

- Derive `Split 1..N` from the ordered SPLIT subset of each Operation's existing `groups` array. Base is excluded even if it is positioned between Splits. No persisted sequence counter, new entity, migration or approval workflow.
- Deleting the middle Split leaves the remaining IDs/names/references untouched, but its successors display consecutive numbers. Appending a Split displays the current count + 1. New Groups store the neutral `Split` name, not a generated ordinal.
- Existing autogenerated `Split`, `Split N` and `Base` names are retained in snapshots and interpreted as default display names. No historical renaming/migration occurs. Existing custom names remain stored and are shown as optional descriptions: `Split 2 · High temperature`. The editable field is labeled `설명 (선택 사항)` / `Description (optional)` and does not edit the system-owned number.
- Shared projection covers Group editor, allocation selector/checkbox labels, duplicate-condition selector, scope Inspector, Draft summary/condition-source column, Create review, Plan grid and newly recorded Delta descriptions. Existing historical Delta strings are not rewritten.
- Identity, Recipe/Parameter/Sample Revision links, conditions/roles, Subject assignment, Snapshot/CAS and evidence locks remain unchanged. New-Delta change detection still uses actual Group identity/content, so replacing a Group cannot disappear merely because its displayed number is reused.

## Acceptance evidence

1. Base + Split 1/2/3 → delete second → Base + Split 1/2 → append → Base + Split 1/2/3.
2. The former third Split retains ID and original stored name. Source snapshot is unchanged; new displayed numbers do not create scientific edits.
3. Native PostgreSQL save/readback repeats the sequence with an existing Group-bound exact Recipe/Source Parameter/Sample R2 link. It asserts identical Source bindings, exact assignments/roles, allocation IDs and custom description after deletion/addition. Existing native contract also checks Plan locks, scoped authorization, immutable Source history and restart persistence.
4. KO/EN SSR verifies contiguous allocation labels and separate optional description input. Custom multiword description input preserves whitespace while typing.
5. Delta regression preserves historical labels and detects real internal-identity changes independently of the displayed sequence.
